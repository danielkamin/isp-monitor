Wariant A — centrum odpytuje obiekty

Wszystkie pomiary wykonuje centrum zarządzania. Zero instalacji na obiektach. Idealny punkt startowy — uruchamiasz w jeden dzień.

Kiedy to wystarcza: Gdy obiekty mają otwarte porty (kamera na 554, alarm na 80/443) lub odpowiadają na ICMP. Pokrywa 80% przypadków bez żadnego deploymentu na miejscu.

Flow danych — Wariant A
1
Probe Service — goroutine scheduler
Co 30s dla każdego obiektu uruchamiana goroutine wykonuje serię 5 pingów ICMP + TCP connect na zarejestrowany port. Worker pool ogranicza równoległość.
// Worker pool — max 20 równoległych probe sem := semaphore.NewWeighted(20) for _, site := range sites { go func(s Site) { sem.Acquire(ctx, 1) defer sem.Release(1) result := prober.Probe(ctx, s) resultCh <- result }(site) }
concurrencysemaphoregoroutines
2
Storage Service — bulk insert przez gRPC stream
Probe Service otwiera długo żyjący gRPC bidirectional stream do Storage. Wyniki są batchwane po 50 rekordów i wstawiane do PostgreSQL w jednej transakcji przez sqlc.
-- sqlc query -- name: InsertProbeBatch :exec INSERT INTO probes (site_id, ts, rtt_ms, packet_loss_pct, is_online, hop_count) SELECT unnest($1::uuid[]), unnest($2::timestamptz[]), unnest($3::float8[]), unnest($4::float8[]), unnest($5::bool[]), unnest($6::int[])
sqlcgRPC streamtransakcje
3
Analytics Service — detekcja incydentów
Subskrybuje eventy ze Storage. Gdy obiekt przechodzi z online→offline otwiera nowy incydent w transakcji. Śledzi baseline latencji per site (rolling average), wykrywa spiki.
// Detekcja przejścia online → offline func (a *Analyzer) onProbeResult(ctx context.Context, r ProbeResult) error { prev := a.cache.Get(r.SiteID) // sync.Map if prev.IsOnline && !r.IsOnline { return a.repo.OpenIncident(ctx, r.SiteID, r.Timestamp) } if !prev.IsOnline && r.IsOnline { return a.repo.CloseIncident(ctx, r.SiteID, r.Timestamp) } return nil }

API Service — dashboard i raporty
REST API + WebSocket push przy zmianie statusu obiektu. Endpointy do raportów per ISP, per obiekt, eksport CSV.

Wariant B — agent na obiekcie

Lekki binary w Go deployowany na RPi Zero 2W lub dowolnym urządzeniu na obiekcie. Daje pełny obraz: co widzi obiekt od środka vs co widzi centrum z zewnątrz.

Kluczowa wartość Wariantu B: Korelacja dwukierunkowa — gdy centrum nie widzi obiektu, ale agent dalej pinguje 8.8.8.8, problem leży po stronie centrum lub routingu asymetrycznego. Gdy agent też traci internet — to awaria ISP po stronie obiektu.

Co robi agent — flow
1
Agent boot — połączenie z centrum
Agent startuje, nawiązuje gRPC keep-alive stream do centrum. Jeśli połączenie pada, exponential backoff + retry. Centrum widzi moment odłączenia agenta jako osobne zdarzenie.
// Agent — reconnect loop for { conn, err := grpc.Dial(centerAddr, grpc.WithBlock()) if err != nil { time.Sleep(backoff(attempt)); continue } err = runStream(ctx, conn) // blokuje do utraty conn conn.Close() attempt++ }
2
Lokalne pomiary co 30s
Agent pinguje: (a) centrum zarządzania, (b) 8.8.8.8, (c) 1.1.1.1. Mierzy RTT i packet loss. Wyniki buforowane lokalnie gdy stream niedostępny.
targets := []string{ "centrum.firma.pl", // twój serwer "8.8.8.8", // Google DNS — referencja globalna "1.1.1.1", // Cloudflare DNS — referencja globalna } // Wyniki wysyłane strumieniem, jeśli offline → local ring buffer
3
Centrum — korelacja i klasyfikacja
Analytics Service ma teraz dwa sygnały per obiekt. Matryca 2×2 daje root cause klasyfikację awarii.
Centrum nie widzi | Agent nie widzi DNS → AWARIA ISP (obiekt bez internetu) Centrum nie widzi | Agent widzi DNS → ROUTING ASYMETRYCZNY lub NAT problem Centrum widzi | Agent nie widzi DNS → AWARIA ISP (upstream agenta) Centrum widzi | Agent widzi DNS → OK (fałszywy alarm — zatkany port)

Migracja A → B

Przejście jest łatwe — Wariant A jest zaprojektowany tak, żeby B był naturalnym rozszerzeniem. Żaden istniejący serwis nie wymaga przepisania.

Szacowany nakład pracy
Napisanie agenta Go (nowy serwis) ~2–3 dni · GOARCH=arm cross-compile
Rozszerzenie Storage Service ~0.5 dnia · dodanie kolumny source + nowe sqlc query
Korelacja w Analytics Service ~1 dzień · matryca 2×2, nowe reguły incydentów
Rozszerzenie .proto (gRPC) ~2h · nowy AgentService, regeneracja kodu
Deploy + hardware na obiekcie ~1 dzień per N obiektów (RPi setup, SSH, autostart)

Ważne przy migracji schematu: Dodanie kolumny source do tabeli probes to prosta migracja ALTER TABLE z wartością domyślną 'probe' — stare dane nie wymagają żadnej transformacji.
Kolejność kroków migracji
1
Migracja schematu DB (backward-compatible)
Dodaj kolumnę z DEFAULT — stary Storage Service nadal działa bez zmian kodu.
-- golang-migrate: 0003_add_source_column.up.sql ALTER TABLE probes ADD COLUMN source VARCHAR(10) NOT NULL DEFAULT 'probe'; CREATE TABLE agent_heartbeats ( site_id UUID REFERENCES sites(id), last_seen_at TIMESTAMPTZ NOT NULL, agent_version TEXT, PRIMARY KEY (site_id) );
2
Rozszerz .proto i wygeneruj kod
Dodaj AgentService do istniejącego pliku proto. Stare usługi nie są dotknięte.
// collector.proto — nowy blok, stary ProbeService bez zmian service AgentService { rpc ReportMetrics(stream AgentMetric) returns (stream AgentCommand); rpc Heartbeat(HeartbeatRequest) returns (HeartbeatResponse); }
3
Napisz i skompiluj agenta
Nowy serwis, ~500 linii. Cross-kompilacja na ARM zajmuje sekundy.
GOOS=linux GOARCH=arm GOARM=7 go build -o agent-arm ./cmd/agent # RPi Zero 2W: GOARCH=arm64 GOOS=linux GOARCH=arm64 go build -o agent-arm64 ./cmd/agent
4
Deploy na obiektach stopniowy (canary)
Zaczyna od 1 obiektu pilotażowego. System działa przez cały czas — Wariant A cały czas zbiera dane. Agent jest addytywny, nie zastępuje probe.
